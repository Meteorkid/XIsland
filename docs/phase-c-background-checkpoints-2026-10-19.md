# 第三阶段：后台检查点补齐

日期：2026-10-19。用户已授权直接修复。本文记录新增实现，阶段整体状态仍以优化计划和真实长稳结果为准。

## 问题与方案

上一轮把 5 万事件的增量保存从约 9.46 s 降至 273 ms，但 SwiftData 关系维护和提交仍同步占用主执行器。复用 Context 无明显收益。本轮沿用原数据库与事务算法，将生产写入移到串行后台执行器；不增加日志格式或 schema 迁移。

生产处理顺序为：接收操作 → 同步更新会话并冻结检查点 → 收集器退出 → 后台按顺序提交 → 主执行器处理成功/失败回执 → 下一项操作。界面继续响应，审批点击立即进入发送中并防止重复提交；实际发送与保存遵循队列顺序。已失效的请求不会因旧点击而被批准。

`SessionSaveWorker` 由同步兼容入口和后台入口共享。后台只接收 Sendable 值快照，自己创建 ModelContext；不会跨线程传递 AgentSession、SwiftData 模型或交互回调。现有同步测试保留，另有专门的生产后台路径测试。

## 不变量

- 排队不等于保存成功。保存成功后才清理未保存集合、确认脏记录版本，或移除被关闭的会话；失败保留事实并允许重试。
- 孩子记录按捕获版本确认，旧回执不能清掉新追加/修改。元数据回填也不能覆盖新状态。
- 孤儿审批事实与父记录同事务转移。连续冻结快照合并同一客户端已提交的身份事实；换客户端身份不继承。观察中断不伪装为任务完成。
- 保存、孤儿、删除与清理共用写入顺序；统计/导出使用独立读取 actor。提交期使已有读取和期间新登记的读取失效，防止发布跨事务结果。no-op 不推进 revision，也不使读取失效。
- 提交期只对登记簿持短锁，不让主线程等待 SQLite 的提交锁。
- 退出先停止接收新操作，等待已经接受的写入及在途审批完成。保存失败取消退出，恢复接收并显示错误；不会把未提交内存状态宣称为可从崩溃恢复的数据。

## 已验证

Release 的检查点生产入口基准、事务/顺序/失败/退出相关共 32 项通过；随后突发消息回归 10 项通过，最终全量 **1371 项、0 失败、0 跳过**。

在 Apple M3 Max 上，5 万事件、5 次生产消息至持久化检查点：事务完成 p95 约 261.68 ms；期间 1 ms 主执行器回调更新可观察搜索状态，额外延迟 p95 1.08 ms、最大 1.75 ms，共 593 个回调样本。重开数据读取核对 50005 条工具记录及其唯一 ID。

这是生产消息入口和模拟交互调度测量，不是物理键盘输入延迟或显示器 FPS。同步兼容 API 仍会阻塞调用者；生产入口使用后台队列。冷历史恢复仍保留旧同步读取路径，不在这项保存基准的结论范围内。

## 长稳与原生验收

固定后台存储测试版本于 2026-10-19 03:11:15—11:11:21 连续完成 28806.605 秒，25140 个事件，恢复与完整导出核对通过；只读 SQLite 独立核验也通过。原测试二进制与当时源码 hash 一致。

长稳之后补修了两个 UI 文件的交互面板高度/尺寸同步，以及测试仪器的 Mach CPU 时间单位。存储生产源码未改变；最终 1380 项回归通过。不能将该长稳宣称为最终 GUI 补丁的整版 8 小时运行。

原生面板按钮、回车/Escape、设置路由及 60Hz/ProMotion 下展开收起已验证；系统设置恢复原值。旁白朗读因原生工具断连未验，实际 FPS 因追踪数据不可用未验，外接多屏缺设备。阶段 C 保留这些出口，详细证据和下一步见第三阶段验收报告。
