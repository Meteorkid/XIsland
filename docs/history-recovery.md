# 历史数据备份与恢复

## 2.0.0 的升级保护

2.0.0 增加了会话来源、观察状态、Kimi 后台任务及工具原生终态的保存。旧工具记录没有原生终态时保持空值，不推断成功、失败或取消；旧会话、聊天及工具标识继续保留。

首次打开已有数据库前，应用会生成新的升级前备份：

```text
HistoryBackups/<数据库文件名>.pre-tool-completion-status-v5.sqlite
```

该标识与 1.x 的备份不同，因此升级期间新增的历史也有本次迁移前的恢复点。旧备份不删除、不覆盖；创建或验证本次备份失败时，不继续打开数据库迁移。恢复方法见下方流程：需要退回 1.x 时使用此次 v5 升级前副本，并保留升级后的原库与 sidecar，避免丢失 2.0.0 新增的历史。

## 1.13.1 的升级保护

1.13.1 为聊天消息和工具事件保存稳定标识，修复重复保存遗漏和记录更新问题。首次打开已有磁盘数据库之前，应用先生成包含已提交 WAL 内容的一致 SQLite 快照，再打开 SwiftData 执行格式升级。

备份位于数据库文件同级的 `HistoryBackups` 文件夹，命名为：

```text
<数据库文件名>.pre-stable-record-ids-v1.sqlite
```

例如数据库文件为 `default.store`，备份文件就是 `HistoryBackups/default.store.pre-stable-record-ids-v1.sqlite`。以实际存储目录为准，不要根据其他应用的数据目录猜测位置。

- 备份经过 SQLite 完整性检查，通过后才原子写入最终位置；已有有效备份不会被覆盖。
- 备份创建或验证失败时，历史库不会继续升级；应用会提示历史未保存，相关内存会话保留供重试。
- 新建数据库和纯内存测试存储不会创建升级前备份。
- 这份备份是首次格式升级前的恢复点，不是持续备份，不包含升级后新增的历史。

## 手动恢复流程

1. 退出所有 X Island 实例，确认后台进程已结束，停止对数据库的写入。
2. 找到实际历史数据库及上述备份文件。先复制整个当前数据库目录到另一个独立保存目录，保留主数据库及对应的 `-wal`、`-shm` 文件，以保护升级后新增的数据。
3. 在独立临时目录复制升级前备份并检查该副本；可执行 `sqlite3 '/实际路径/备份副本.sqlite' 'PRAGMA integrity_check;'`，结果应为 `ok`。不要直接修改唯一的备份原件。
4. 在应用退出状态下，把当前数据库及其 `-wal`、`-shm` 移到保留目录；将已验证的备份副本复制回数据库原路径并恢复原文件名，避免旧 WAL 覆盖恢复的数据。
5. 如需退回旧版，先更换到与该备份对应的原应用版本，再启动并检查历史数量、聊天内容及工具结果；如继续使用新版，启动后会重新执行兼容升级。
6. 确认数据正确前保留当前库副本和升级前备份，不合并未知状态的数据文件。

测试使用独立临时数据库覆盖 WAL 内容、不可写备份位置、损坏文件、禁止覆盖，以及用旧 schema 只读打开恢复副本。用户自己的数据库不参与发布测试。
